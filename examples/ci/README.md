# GitHub and CI Integration Example

[日本語 / Japanese](README.ja.md)

This example supports Chapter 8's question: **What exact revision and inputs were checked?** It runs the 107 model tests and records the Git revision checked out, SHA-256 of tracked inputs, Python version, command, outcome, and logs. It does not establish that business requirements are complete or grant permission for production deployment.

## Run locally

Place these materials at the root of a Git repository, commit the tracked files, and use a clean working tree. From that root:

```bash
python examples/ci/collect_lab_result.py --output ci-results
```

Git and Python are required. This generates `ci-results/ci-result.json` and `ci-results/unittest.log`; the output directory is excluded from tracking. If `GITHUB_SHA` is set, the collector compares it with the actual checked-out `HEAD`.

The CI recorder has eight unit tests, separate from the companion model suite:

```bash
python -m unittest discover -s examples/ci -v
```

A local Git-based run successfully recorded 107 passing model tests. Tests also covered rejection when the event SHA differs or tracked changes have not been committed. This does **not** establish that the workflow has successfully run on GitHub.

## GitHub Actions

A proposed workflow lives at `.github/workflows/lab-checks.yml`. With a published repository and GitHub Actions enabled, it is intended to run on `pull_request`, `merge_group`, and pushes to `main`. The workflow uses `contents: read`; it does not receive production secrets or deployment authority. The first remote run and artifact upload **remain unverified**.

## Trust boundary

A JSON record generated by the code being proposed in a PR has the same trust scope as that PR. A self-reported `PASS` cannot be directly promoted into a privileged deployment authorization. A separate protected decision path must verify the execution environment, workflow definition, Git target revision, and relevant artifact provenance.

This example is not a replacement for a security review of `pull_request_target` or `workflow_run` usage. It is neither a complete SLSA attestation pipeline nor a production admission controller.
